### Архив прогона (chore/raw-archive, v1.10)

Прогон не моложе N = `after_days` дней по дате МСК метки (по умолчанию N = 0 —
любой загруженный прогон; решение Андрея 21.10: упаковка в 22:30, бэкап в 23:00), уже загруженный в базу,
упаковывает `scripts/pack_runs.py` (модуль `run_archive`) в один архив:

- место — `[paths] archive_dir` в `config.toml` (по умолчанию `data/runs_xz`;
  нет каталога — упаковщик создаёт его), вне каталога `runs/`: сборщик,
  ротация и сторож его не видят. Не путать с
  `data/archive/`, куда убирают пробные и оборванные папки;
- имя — `<метка>.tar.xz`; пока пишется — `<метка>.tar.xz.part`, после
  проверки — `fsync` и переименование. Файлы `.part` загрузчик пропускает;
- внутри всё под каталогом `<метка>/`: ровно файлы отпечатка E-65 (перечень
  выше без `raw/*.html` и `raw/*.html.gz` — HTML страниц в архив не идёт, его
  по-прежнему удаляет ротация через 30 дней, E-41). Каждый `raw/*.json.gz`
  (страница и `_broken_*.json.gz`) лежит распакованным под именем без `.gz`;
  остальные файлы — байт в байт. Посторонние файлы (.DS_Store) не идут;
- в корне архива, рядом с каталогом `<метка>/` (не внутри него) —
  `<метка>.sha256`: sha256 исходных файлов как они лежали на диске, формат
  `sha256sum`, по путям от каталога прогона (для аудита). В распакованной
  папке прогона манифеста нет, поэтому в хэш прогона он не входит;
- хэш каталога прогона и хэш его архива равны (E-65): так проверяется
  упаковка и так загрузчик получает ту же базу из архива, что из папки;
- загрузчик для метки берёт архив, если он есть, иначе папку; в
  `slices.path` пишется путь архива. Исходные папки упаковщик не удаляет;
  файлы описи (кроме `summary.json` и `night.log`) удаляет бэкап после сверки
  архива на тестовом сервере (E-90, PR #90), HTML — ротация (E-41).

## 2. raw/<sector>_p<N>.json.gz — главный файл для БД

```json
{"totalOffers": 161, "offers": [ {...}, {...}, ... ]}
```
(gzip-обёртка; ЗАГРУЗЧИК ОБЯЗАН читать и `.json.gz`, и голый `.json` — на случай
несжатых остатков в исторических каталогах.)

- `<sector>` — ключ полигона из geojson: сектор (`41`, `D3`) или клетка сбора (`T0706`, `T0713ca` — см. §8); **внутри файла имени сектора НЕТ**,
  ключ только в имени файла. Название/статус сектора — в `plan.json`/`summary.json`
  прогона или в `cian_sectors_v2.geojson`. Терминология E-29: **ключ сектора**
  (`properties.sector`) — техническая метка, неизменяем, не переиспользуется;
  **название** (`properties.name`) меняется свободно и ключом не является.
- `offers` — элементы «как у ЦИАН», без обработки. Эталон структуры сырья —
  фикстура БД `tests/fixtures/cian/*.json.gz`: страница боевого `raw/*.json.gz`
  дословно. Карта полей и типы — RECON §3; упомянутый там `cian_serp_sample.json` —
  разбор HAR от 07.09, ОБРАБОТАННАЯ выборка, только карта полей: его поле
  `geo.address_short` в сырье не встречается (0 из 85 751 оффера по 12 прогонам,
  скан 25.09); адрес-строка в сырье — `geo.userInput` (непуст у каждого
  оффера). (Прежняя формулировка v1.4 «других полей адреса нет» неверна:
  есть разобранный адрес `geo.address`, ниже.)
- `geo.address` (v1.9) — список частей адреса; у каждой части `type`
  (вид части; нужная нам — `house`), `id` (число в справочнике ЦИАН) и `name`
  (строка). Часть дома — `type="house"`, её `name` — номер дома как в
  справочнике («283», «950»; эталон — фикстура Р1: оффер 322083896 → «283»,
  оффер 330231571 без части дома). Номер дома используется в гео-склейке
  [E-78]. Факты (data-checker 19.10, 52 прогона, 507 377 объявлений):
  часть `house` есть у 38,1 % объявлений; две и больше частей `house` — 0;
  пустых и нестроковых `name` — 0; `geo` без `address`, с `address: null` или
  с пустым списком — 0 (для надёжности загрузчик такое тоже принимает: номер
  дома пуст). Один и тот же адрес в справочнике бывает заведён с двумя `id`
  (пример: «Раменский, Фортуна, Заречная, 23» — `id` дома 11305721 и
  14047358), поэтому склейка `id` дома не сравнивает. `name` дома у одного и
  того же `id` между прогонами меняется у 53 из 15 542 повторяющихся `id`
  (пример: объявление 288271196, «950» → «958»): продавец правит адрес, номер
  дома публикации перезаписывается значением среза [E-52].
  Рабочие поля: `id` (int), `bargainTerms.price`, `geo.coordinates.{lat,lng}`,
  `land.area` (строка, бывает числом — приводить), `fullUrl`, `addedTimestamp`,
  `cianUserId` и др.
- ≤28 офферов на страницу; последняя страница обычно короче.
- `totalOffers` — счётчик ЦИАН на момент запроса; может слегка плавать между страницами
  одного сектора (живой рынок). Реальное число уникальных лотов = объединение id по
  страницам. «Собрано ≈ заявлено» верно только с учётом скрытых в блоках
  девелопера (`similar`, ниже): заявлено (`totalOffers`) = собрано + скрыто в
  блоках + недобор. Недобор ЦИАН при честно законченной выдаче (последняя
  страница короткая, `totalOffers` одинаков на всех страницах) бывает: клетка
  `T0608` — в 37 прогонах сетки недобор 12–14 при заявлено 167–176, доля ≈ 92%;
  что за недостающие объявления — в сырье не видно. Часть расхождения — повторы
  id на соседних страницах: `T0605`, прогон `2026-09-20_1131` — на страницах 127
  объявлений, уникальных 105 (22 повтора); сборщик повторы отбрасывает при
  учёте. `complete` — по короткой странице или по всем страницам, запланированным от
  счётчика (`night.is_complete`, `collector/night.py`); число собранных id со
  счётчиком сборщик не сравнивает; правило дочитанности —
  E-66. Отчёт, раздел «Правило Р2».
- `similar` у объявления выдачи: `null`, `{"count": N, "url": …}` или ключа нет
  вовсе (246 из 514 838 объявлений, data-checker 15.10). `count > 0` —
  объявление-представитель блока девелопера: скрытые объявления (N штук) в
  выдаче не отдаются, их id в сырье нет; сборщик хранит только представителя.
  `count = 0` ничего не прячет. Скрытые в блоках не отслеживаются (E-67) и
  учитываются только в правиле дочитанности (E-66). Отчёт, раздел «Группировка
  девелопера в выдаче».
- Один и тот же id МОЖЕТ встретиться на двух страницах (дрейф между запросами):
  дедупликация по id обязательна. Ночные срезы чище дневных (0–4 дубля против ~40).
- Метка времени конкретной страницы — строка `n=… sector=… page=…` в `night.log`.

## 3. summary.json — паспорт среза (ключевой для отбора и привязки)

Верхний уровень: `night` (дата старта), `dry_run`, `budget`, `spent`,
`stopped` (`queue_empty` = полный срез | `budget_exhausted` | `block` | `net_error` |
`api_changed` | `interrupted` | `smoke_only`), `stop_class`, `stop_detail`, `smoke`,
`ticket` (bool), `cookie_age_h`, `ladder_step_valid`, `ladder_result`
(`passed`/`blocked`/`invalid`/`smoke_only`), `sectors_touched`, `sectors_complete`,
`duplicate_ids_total`, `stateless_pagination_ok`, `served_vs_total_median`,
`sectors` — словарь по ключу сектора:

```json
"63": {"name": "Сектор 63", "status": "рабочий", "total_offers": 161,
       "pages_planned": 6, "pages_done": [1,2,3,4,5,6], "served_end": true,
       "unique_ids": 160, "duplicate_ids": 0, "complete": true,
       "served_vs_total": 0.99}
```

- `complete` — сектор снят целиком (дошли до конца отдаваемого набора или закрыли все
  страницы верхней оценки). `served_end=true` — конец набора увидели явно
  (короткая/пустая страница или 301→p=1).
- `pages_planned` — верхняя оценка из totalOffers; реальный конец может быть раньше.
- **Инвариант (v1.5):** у каждого полигона `unique_ids + duplicate_ids` = числу
  элементов `offers` по всем его страницам `raw/<ключ>_p<N>.json{,.gz}`; то есть
  `duplicate_ids` — повторы id сверх первого вхождения. Проверено 25.09 на всех 12
  прогонах локальной копии `data/runs/`: 9 прогонов секторов (`2026-09-15_1529` …
  `2026-09-19_1121`, по 45 полигонов) и 3 полных прогона сетки (`2026-09-20_0108`,
  `2026-09-20_1131`, `2026-09-20_2324`; 114/112/112 полигонов) — 743 полигона,
  расхождений 0. В выборке: 29 полигонов с дублями (197 дублей), 2 разрезанных
  родителя (`complete=false`), 9 пустых полигонов (`unique_ids = 0`).
- **Контур сетки (calib2)** добавляет: у каждого полигона — `level` (0 = клетка 10 км,
  1/2/3 — глубина нарезки; у секторных прогонов ключа level нет ни у одной клетки (пример: 2026-09-15_1529, 45 клеток); клетки очереди в summary.json не записаны (только plan.json → pending_sectors); ключ, который есть в обоих списках, level имеет (2026-10-08_0032: 19 клеток summary, level у всех, pending 97, из них в summary 1); v1.7), `parent` (ключ родителя или null),
  `split` (bool: клетка разрезана В ЭТОМ прогоне), `children` (ключи детей);
  на верхнем уровне — `split_events` (список `{parent, total_offers, children}`),
  `tile_mode` (bool), `split_threshold` (порог, 400), `collect_file` (имя файла клеток).
  РАЗРЕЗАННЫЙ РОДИТЕЛЬ ВСЕГДА `complete=false` — его покрытие живёт в детях (E-21/E-42);
  снятая им страница 1 в raw/ есть, но срезом родителя не является.

## 4. plan.json и night.log

`plan.json` — то же ядро + `started_at`, `window_hours`, `mean_interval_s`,
`user_agent`, `seed`, `done` (список задач с состояниями
`done`/`page_end`/`net_error`/`failed`), `pending_sectors`. Атомарно перезаписывается
после каждого запроса — по нему видно живой прогон.

- **Для загрузчика `plan.json` обязателен (v1.6):** полигоны среза = ключи
  `summary.json → sectors` ∪ `pending_sectors` (ТЗ E-42, TEST_PLAN S-5); нет файла —
  прогон не грузится. `summary.json → sectors` содержит только полигоны с прочитанными
  страницами (`pages_done`).
- `sectors` — словарь по ключу, как в summary.json; `done` — список задач
  `{sector, page, kind, origin, attempts, state, detail}`.
- `pending_sectors` — список строк-ключей (`["T0713", "T0706"]`): полигоны, до которых
  прогон ещё не дошёл. Дети нарезки вставляются в него такими же строками в СЛУЧАЙНУЮ
  позицию; порядок списка ничего не значит. В законченном полном прогоне пуст (ФАКТ:
  пуст во всех 12 прогонах `data/runs/`, скан 26.09; сейчас прогонов больше — §1).
- Smoke-клетка: `Night.smoke` читает страницу 1 случайной мелкой клетки и кладёт её в
  `sectors` (`pages_done=[1]`), но из `pending_sectors` не убирает — обход потом
  начинает её со страницы 2. Обрыв прогона до её очереди → ключ одновременно в
  `sectors` и в `pending_sectors`; для загрузчика это один полигон по записи summary.

`night.log` — строки `ISO-время \t k=v \t k=v ...`. Запросы:
`n= sector= page= kind=(smoke|ssr) http= ms= offers= bytes= total= verdict= err=`.
События: `event=start` (budget, window_h, ticket, cookie_age_h, order),
`event=sector_end` (why=short_page|redirect_to_p1_301|empty_page|smoke_empty),
`event=retry` (attempt, of, after_s), `event=STOP` (reason, cls, detail, spent).
Вердикты: OK, PAGE_END (не отказ), BLOCK, API_CHANGED, NET_ERROR.

## 7. Известные ограничения формата

- Файлы сырья не самодостаточны (нет имени сектора, времени, URL внутри) — сопоставление
  через имя файла + summary.json. Если понадобится самодостаточность, это одна правка
  в `run_folder.write_page` (обёртка вокруг ответа); старые файлы останутся как есть.
- `stateless_pagination_ok` — строгий флаг «дублей ровно 0»; False при 1 дубле — не сбой.
- До 13.09 включительно структура каталогов иная (без времени в имени) и данные частичные.
- Исторические прогоны (до 18.09): HTML только у страниц 1; их json сжаты на месте 18.09
  (gzip, без потери данных). polygons.geojson.gz добавлен в них бэкфилом 19.09
  (backfill_polygons.sh): содержимое = точная копия cian_sectors_v2.geojson (sha256
  распакованного = 71d921398f43dba3e29d5bdb61f3b9ec09322aeef7223a87c4a8ac5a947d4c4c);
  байты .gz могут отличаться от питоновских — сверять распакованное. Иных изменений
  формата задним числом нет.

## 8. Контур сетки клеток (calib2, с 18.09) — ключи, нарезка, discovery

- **Ключ клетки**: `T<ряд><колонка>` уровня 0 (`T0706`) + суффикс букв `a–d` на каждый
  уровень нарезки (`T0706a`, `T0706ab`): a=ЮЗ, b=ЮВ, c=СЗ, d=СВ четверть базового
  квадрата родителя. Ключи детерминированы, неизменяемы, не переиспользуются (E-29/E-42).
- **Авторазрезание**: totalOffers страницы 1 > 400 → родитель выбывает НАВСЕГДА, 4
  четверти (± нахлёст ~25 м/сторона) ∩ полигон родителя встают в очередь ТОГО ЖЕ среза;
  пустые четверти (за границей области) не создаются. Дно `level=3` (~1.25 км): клетка
  не делится, а листается (решение Андрея 18.09). Событие в summary → `split_events`.
- **Файл клеток** (`cian_collect_tiles_*.geojson`) ведёт СКРИПТ (атомарная перезапись):
  у разрезанного родителя `collect=false, status=split, split_at, children`; дети
  добавляются фичами (`level`, `parent`, `base` — базовый квадрат, канон округлён до
  7 знаков). Загрузчик этот файл НЕ читает (охват — только из polygons.geojson.gz
  прогона); файл секторов скрипт не трогает никогда. Снапшот для знаний —
  cian_collect_tiles v0.4 (21.09).
- **Режим `--discovery`** (убран из сборщика в PR #121; прогоны, сделанные им, остались в данных): только первые страницы всех клеток (волна totalOffers),
  нарезка активна; клетки с total>28 остаются `complete=false` — по E-21 такой прогон
  снятий не порождает.
- **Прогоны лестницы на 186.246.4.168** (18–21.09): `2026-09-18_1722-smoke` и
  `2026-09-18_2306` (discovery) — БЕЗ снимка polygons.geojson.gz (версия скрипта до
  R-1; решение Андрея 19.09 — не бэкфилить) → в БД не грузятся. Полные срезы сетки со
  снимками: `2026-09-20_0108`, `2026-09-20_1131`, `2026-09-20_2324` (497/494/495
  запросов, queue_empty). Протокол и факты — CIAN_CALIBRATION_TASK_2 v1.0.
- **Smoke-запрос и `spent` (v1.6, по коду сборщика):** `done` в plan.json пополняет
  только обход (`Night.step`); smoke-запрос (`Night.smoke`) тратит `spent` и пишет в
  night.log строку `kind=smoke`, но в `done` не попадает. Инвариант: `len(done)` +
  число строк `kind=smoke` в night.log = `spent` (`spent` в summary.json = `spent` в
  plan.json). Если первый smoke-сектор пуст, берётся следующий — smoke-строк две.
  ФАКТ (скан 26.09): инвариант верен на всех 12 прогонах `data/runs/` (тогдашних; сейчас — §1); две
  smoke-строки только в `2026-09-20_1131` (`T0713caa` пустой → `T0713cab`).
  Инвариант относится к ЦЕЛОМУ прогону: в мини-фикстуре `done` урезан по ключам, а
  smoke-строка остаётся, только если её сектор среди ключей.
