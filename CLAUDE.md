# ads_collector — инструкции для Claude Code

Читается в начале каждой сессии. Короткий намеренно: только правила работы. По умолчанию сессия — тимлид (§4).

## 1. Что это

Сборщик ЦИАН — отдельная программа: обходит выдачу ЦИАН по клеткам сбора и пишет папку прогона. Пакет `collector/` (стандартная библиотека; внешняя httpx — только в `httpx_transport.py` и только при `--transport httpx`), инструменты разработчика — `scripts/`, тесты — pytest. Переехал из land-monitor (коммит 881658d, после PR #122). land-monitor сборщик не импортирует: он читает папки прогона по формату `docs/CIAN_DATA_FORMAT.md`.

Владелец — Андрей. Код в PR он не читает: читает описания PR, отчёты и вопросы уровня 2. Код проверяют `reviewer` и локальный прогон проверок (§7).

## 2. Главная цель кода

Код пишется для людей, а не для машин. Из двух решений выбирай то, которое проще прочитать, даже если оно длиннее или медленнее. Непонятное место в диффе — дефект кода, а не читателя.

## 4. Роли и цикл одного блока

Основная сессия — **тимлид**: одна задача в одной сессии. Всю работу он делегирует субагентам из `.claude/agents/` и сам не пишет ни тестов, ни кода: читает результаты, принимает решения уровня 1, выносит вопросы уровня 2, ведёт `docs/DECISIONS.md`, `CURRENT_TASK.md` и `TEAMLEAD_REPORT.md`. Задачи выдаёт PM (сессия в land-monitor); обмен — через git: задание → `CURRENT_TASK.md`, итог → `TEAMLEAD_REPORT.md`.

| Роль | Что делает | Что передать в промпте |
|---|---|---|
| `planner` | план блока: кейсы, функции, сигнатуры, оценка кода и тестов отдельно, общие файлы, вопросы уровня 2 | задание, кейсы, решения уровня 1 прошлых блоков |
| `architect` | хранитель простоты, владелец раздела 2 `collector_architecture.md`: вызов 1 — план на KISS; вызов 2 — сверка диффа с разделом 2 и его обновление | вызов 1 — план; вызов 2 — ветка |
| `test-writer` | коммит «тесты»: красные тесты по кейсам, имена = номера кейсов; пишет только в `tests/` | план (сигнатуры, кейсы), ветка |
| `coder` | коммит «код»: реализация до зелёного в `collector/`, `scripts/` и названных `docs/`; `tests/` не трогает | план, ветка, ответы тимлида на вопросы |
| `reviewer` | независимое ревью диффа, оспаривает решения уровня 1; режимы «часть» и «ревью тестов» | ветка, решения уровня 1 блока, вывод прогона перед push; для части — номер и файлы; для ревью тестов — sha и кейсы |
| `data-checker` | утверждения о сырье ЦИАН проверяет по `collector/`, фикстурам и (если есть) полным прогонам вне репозитория; отвечает цифрами | точная формулировка утверждения |
| `docs-keeper` | сверка документов между собой и с кодом; правит только документы | ветка, какие `docs/` менялись |

Субагент стартует с чистым контекстом: пути, номера кейсов, решения и правила окружения (§8) передаются в промпте явно. Проверяющие (`reviewer`, `data-checker`, `docs-keeper`) не получают рассуждений автора — только файлы. Меняющие файлы (`coder`, `test-writer`, `docs-keeper`, `architect` с правками) — строго по одному и с ожиданием результата, не в фоне; параллельно — только читающие (`reviewer`, `data-checker`). Пришёл промежуточный итог — тимлид сам сверяет коммиты и файлы и идёт дальше.

Один блок = одна ветка = один pull request.

0. Андрей вставляет задание от PM. Ветка от свежего `main` — `block/<кратко>` (служебные — `chore/<кратко>`); первым коммитом задание дословно в `docs/process/CURRENT_TASK.md`.
1. `planner`. Перечень общих файлов из плана тимлид сверяет со строкой «Общие файлы» задания.
2. `architect`, вызов 1: план на KISS. «Упростить» — `planner` переделывает.
3. Вопросы плана — по §4а: уровень 1 тимлид решает сам и пишет в `docs/DECISIONS.md`; остановка — только по новой внешней библиотеке; прочий уровень 2 — «допущение» в раздел 6 описания PR. Вопросы, возникшие позже, — так же.
4. `test-writer` → коммит «тесты»: красные тесты, кода реализации нет.
5. `reviewer`, режим «ревью тестов» — один круг, до `coder`; замечания исправляет `test-writer`.
6. `coder` → коммит «код»: до зелёного, тесты не меняются. Считает тест неверным — не правит, возвращает тимлиду с обоснованием.
7. Спор «как устроено сырьё» — `data-checker`, не обсуждение.
8. Проверки §7, затем `git push` ветки и `gh pr create` с описанием по `docs/PR_TEMPLATE.md` (правки — `gh pr edit`); в описании — раздел «Решения уровня 1» (копия строк DECISIONS).
9. `reviewer` — один круг. Исправить все БЛОКЕР и «стоит поправить» (через `coder` / `test-writer`), повторить проверки и push. Второй круг — только если был БЛОКЕР или правка затронула логику (поведение кода или проверка в тесте); не больше двух. Дифф без `docs/` больше ~800 строк — частями по ~600–800 строк, по `reviewer` на часть параллельно. Каждое несделанное замечание — в раздел 8 описания PR с причиной.
10. `architect`, вызов 2: сверка диффа с разделом 2 `collector_architecture.md`.
11. `docs-keeper`: ссылки, кейсы, имена, устаревшие формулировки.
12. Последним коммитом тимлид перезаписывает `docs/process/TEAMLEAD_REPORT.md` (≤40 строк: задача и «PR #N»; что сделано; кейсы; решения уровня 1 ссылкой на строки DECISIONS; открытые вопросы уровня 2; ошибки в ранее слитом коде; открытые места; рекомендация следующего шага; какие `docs/` менялись) и делает push. Понадобился ещё коммит — отчёт обновляется и снова идёт последним.
13. Короткая сводка Андрею (§9). Стоп. Сливает PR только Андрей.

## 4а. Уровни решений

| Уровень | Кто решает | Критерий |
|---|---|---|
| 0 | `planner` / `coder` сами | ответ есть в тест-плане, описании формата, CLAUDE.md или `docs/DECISIONS.md` |
| 1 | тимлид; строка в `docs/DECISIONS.md` | реализация без изменения поведения, закреплённого тест-планом, и формата папки прогона; обратимо; в русле принципов (KISS, TDD, «ошибки громко»); в пределах одного блока |
| 2 | Андрей | изменение формата папки прогона или закреплённого поведения; новый модуль, внешняя зависимость, слой абстракции, фоновый процесс; всё, что касается сервера и выкатки; скоуп больше одного блока; противоречие между документами; тимлид не уверен в уровне |

Формат строки `docs/DECISIONS.md`: `- 2026-11-11 · block/move-from-land-monitor · <решение одной фразой> · почему · [обратимо / необратимо]`. Сомнение между 1 и 2 — всегда уровень 2.

Тимлид останавливается и ждёт ответа только по новой внешней библиотеке. Весь прочий уровень 2 — «допущение»: тимлид берёт свою рекомендацию и идёт дальше, вопрос с пометкой «допущение» — в разделе 6 описания PR; Андрей отвечает до слияния, не согласен — правка в том же PR. Вопросы о данных и формате папки прогона — ещё и с пометкой «о данных — ответ до слияния», в разделе 6 первыми.

Формат вопроса (и допущения): объяснение простыми словами → варианты таблицей → рекомендация → последней строкой «Меняет план: да/нет» («да» — новая задача, порядок очереди или скоуп; такой вопрос Андрей пересылает PM).

## 5. Жёсткие запреты

- Никаких сетевых запросов к ЦИАН и вообще наружу — никогда: ни из тестов, ни командами сессии. Сборщик локально не запускать — только pytest, тесты подменяют сеть.
- Никаких ssh, scp, rsync и действий с cron. На сервере до выкатки работает старый файл `~/calib2/cian_calib.py`; выкатка — отдельная задача по команде Андрея.
- Не коммитить и не пушить в `main`; без `push --force` и переписывания истории; `gh pr merge` запрещён — сливает только Андрей.
- Не добавлять зависимости и не устанавливать пакеты; в `collector/` — только стандартная библиотека, кроме httpx в `httpx_transport.py` (решение Андрея 11.11). С транспортом по умолчанию сборщик обязан работать голым python3.
- Исходники стандартной библиотеки и установленных пакетов — читать только Read; поиск в них — `git grep --no-index -n -e '<шаблон>' -- <путь>` только для путей внутри папки репозитория (`.venv/…`), шаблон в одинарных кавычках; вне её — только Read; правку там не делать.
- Не читать `.env`; никаких секретов (куки, UA-файлы билета, токены) в коде, тестах и логах.
- Не менять содержимое фикстур с реальными данными (`tests/fixtures/`).
- Формат папки прогона не менять без решения Андрея (§3).
- Команды git — из корня репозитория, без флага `-C`.
- `../land-monitor-raw` — только чтение: там ничего не менять и не коммитить.

## 6. Правила кода

Пакет `collector/` (устройство — `docs/reference/collector_architecture.md`, раздел 2):

| Файл | Что делает |
|---|---|
| `cian_collect.py` | запуск и края: argv → `Settings` (`read_settings`), сборка обхода (`build_crawl`: seed, часы `Clock`, `rnd`, файл клеток `TilesFile`), край `enter_cian` (билет, выбор транспорта `make_transport`, сборка сайта ЦИАН `CianSite`), `main` в 4 строки |
| `transport.py` | интерфейс сети `Transport` (один метод `get`), сырой ответ `HttpReply`, `NetworkFailure`, общие помощники реализаций; без сети |
| `urllib_transport.py` | транспорт на urllib (по умолчанию): доставить запрос и принести байты, банк кук |
| `httpx_transport.py` | транспорт на httpx (`--transport httpx`); единственное место импорта httpx |
| `page_fetch.py` | сайт ЦИАН над транспортом: заголовки браузера, распаковка тела, длительность, сбой → код 0; `CianSite`, `FetchedPage`, входной билет `Ticket` |
| `crawl.py` | обход: `Settings`, `Clock`, состояние; правила обхода без внешнего мира; текст итога `summary_text`; класс `Crawl` (`collect`, `print_summary`) |
| `search_page.py` | контракт ЦИАН: ссылка на страницу поиска, разбор страницы, классы ответа, константы контракта; чистый |
| `geometry.py` | геометрия клеток (чистые функции) и файл клеток `TilesFile` (чтение `tiles`, `grid()`, атомарная перезапись `record_split` — внизу) |
| `run_folder.py` | папка прогона: `RunFolder` (имена, кодировки и порядок записи файлов) и `say` — единственная печать обхода |
| `status.py` | отдельный скрипт «идёт ли сбор»; пакет не импортирует |

Тесты — `tests/test_collector.py`, `tests/test_collector_transport.py`, `tests/test_collector_nights.py`, `tests/test_collector_status.py`, помощники — `tests/collector_support.py` (фальшивый транспорт `FakeTransport`, фальшивые часы).

### Как писать код: «читается как рецепт»

Код читают сверху вниз без пояснений (решение Андрея 13.11). Образец — эта картинка:

```python
def main() -> None:
    settings = read_settings(sys.argv[1:])
    # вся сборка внешнего мира: часы, rnd, билет, транспорт
    crawl = build_crawl(settings)
    crawl.collect()
    crawl.print_summary()
```

Это схема. Фактический `main` — в `collector/cian_collect.py`: транспорт приходит аргументом `transport_factory` (точка подмены в тестах), а билет и транспорт собирает край `enter_cian`, который обход зовёт после паузы старта (порядок случайности).

- `collect` — один экран сверху вниз: случайная пауза старта → пока есть клетки и бюджет: взять клетку, скачать её, пауза между клетками → итог. Отдельного шага пробы нет: проба — страница 1 первой клетки очереди.
- `download_tile` — один экран: страница 1 → стоп / деление на четверти / страницы 2…N до конца.

Правила:
- **`main` — на языке дела**: несколько строк, каждая — шаг, понятный без кода ниже.
- **Главный алгоритм — на одном экране** (до ~40 строк), без повторов, сна и записи файлов внутри.
- **Класс = предмет реального мира**: файл клеток (`TilesFile`), папка прогона (`RunFolder`), обход (`Crawl`), сайт ЦИАН (`CianSite`); страница поиска — остаток упрощения (`docs/ROADMAP.md`). Не «сумка» полей и не «менеджер».
- **Имя метода — фраза о действии**: `download_tile`, `split_into_quarters`, `pause_between_pages`.
- **Повторы, паузы и запись файлов — в своих функциях**: главный метод о них не знает (повторы при сбое сети — внутри «скачать страницу»).
- **История решений — в `docs/DECISIONS.md` и git**; в коде «почему» — одной строкой со ссылкой на кейс или решение.

### Общие правила кода

- **Импорты.** Никто в пакете не импортирует `cian_collect`; `search_page`, `geometry`, `run_folder`, `transport` не импортируют никого из пакета. Реализации транспорта импортирует только `cian_collect`, `httpx_transport` — только внутри функции (`make_httpx`), не на верхнем уровне модуля. Список транспортов — один словарь `TRANSPORTS` в `cian_collect.py` (решение Андрея 12.11). Сеть (`socket`, `urllib.request`, `http*`) — только в `urllib_transport`, httpx — только в `httpx_transport`. Порядок слоёв: `crawl` → `page_fetch` → `transport`, `search_page`; `crawl` берёт из пакета только `page_fetch`, `search_page`, `geometry`, `run_folder` — транспорт только через `page_fetch` (решение Андрея 12.11). Импорты абсолютные (`from collector import search_page`). Страж — тест 21.78.
- **Внешний мир** (сеть, часы, сон, случайность, argv) — только по краям: в `cian_collect.py` и реализациях транспорта; внутрь он приходит аргументами (транспорт через `enter_cian` → `CianSite`, часы `Clock`, `rnd`). Диск — только `run_folder.py`, низ `geometry.py`, чтение билета и проверка, что файл клеток и файлы билета есть (`cian_collect.py`).
- **Числа сборщика** — в `Settings` (`collector/crawl.py`) и константах контракта в `collector/search_page.py`, не россыпью по коду (решение Андрея 10.11; `collector_architecture.md`, вопрос 2). Исключения: тайм-аут сети `HTTP_TIMEOUT_S` и домен кук билета `COOKIE_DOMAIN` — в `transport.py`, умолчания аргументов запуска (`BUDGET`, `WINDOW_HOURS`, `RUNS_DIR`, `TRANSPORT`, `COOKIES_FILE`, `UA_FILE`) — в `cian_collect.py`.
- Правила — чистыми функциями: данные на входе, результат на выходе. Данные — `dataclass` с подсказками типов.
- Без иерархий наследования, метапрограммирования, декораторов «для красоты» и плотных однострочников. Абстракция — когда одинаковый код встретился в третий раз.
- Функция делает одно дело, ориентир — до 40 строк; больше 5 аргументов — собрать в `dataclass`; ранний выход вместо вложенных условий.
- Идентификаторы — английские, по словарю §10; комментарии, docstring, сообщения коммитов и описания PR — по-русски.
- Комментарий объясняет «почему», а не «что», и ссылается на кейс или решение. Шапка каждого модуля, 5–8 строк: что делает, что получает и отдаёт.
- Ошибки — громко: никаких пустых `except` и молчаливого исправления данных; сообщение называет файл, ключ или параметр.
- У каждой ветки обработки ошибок есть тест, либо этой ветки нет.
- `# pragma: no cover` — только с решением Андрея и комментарием «почему» рядом.
- `scripts/` — инструменты разработчика: TDD не обязателен, встроенные проверки результата обязательны; нашёл расхождение — падает с ошибкой, а не чинит молча.

## 7. Тесты

- Имя теста = номер кейса: `test_21_36_pause_lower_bound`; в docstring — формулировка кейса. У кейса может быть несколько тестов с тем же номером.
- Тесты не ходят в сеть (автофикстура `no_network` в `tests/collector_support.py`), не зависят от текущего времени и порядка запуска. Фикстуры с реальными данными не правятся.
- Покрытие `collector/` — 100 % с ветвлениями (порог — в `pyproject.toml`).
- В работе — только файлы тестов своего блока: `<python> -m pytest -q tests/test_<файл>.py`.
- Перед каждым push — один раз (`<python>` и `<ruff>` — абсолютные пути из §8): `<ruff> check .`, `<ruff> format --check .`, `<python> -m mypy` и полный набор `<python> -m pytest -q -n 4 --cov --cov-report=term-missing`.
- Проверки GitHub сейчас не работают (кончились минуты Actions, решение Андрея 11.11): рассчитывать только на локальный прогон; его вывод — в раздел 4 описания PR.
- Тесты — только командой `<python> -m pytest -q …` (аргументы — файлы, `-k`, `-n`, `--cov`), без конвейеров (`| grep`, `| tail`) и цепочек.

## 8. Окружение на Mac Андрея

- Своё окружение — `.venv` в корне, собирает Андрей скриптом `scripts/setup_env.sh` (решение Андрея 11.11). Python и ruff — абсолютным путём:
  - `/Users/andrei/Documents/Projects/PythonProjects/ads_collector/.venv/bin/python -m pytest -q …`
  - `/Users/andrei/Documents/Projects/PythonProjects/ads_collector/.venv/bin/ruff check .` и `… ruff format --check .`
  - `/Users/andrei/Documents/Projects/PythonProjects/ads_collector/.venv/bin/python -m mypy`
- Не создавать и не пересобирать окружение, ничего не устанавливать: новая зависимость — вопрос Андрею, ставит он сам. Окружение land-monitor (`../land-monitor-raw/.venv`) не трогать.
- Команды bash — простые: без `$…`, `$(…)`, `;` и `&&`. Запуск — из корня репозитория.
- Поиск по файлам — `git grep -n -e '<шаблон>' -- <пути>`; шаблон только в одинарных кавычках; в командах Bash нет обратных кавычек, `$` и подстановок; если Grep/Glob есть в сессии — можно ими (решение Андрея 13.11). Не grep/rg/find через Bash, без `cd` и конвейеров (`|`).
- Разовые опыты — файлом в `var/scratch/` (Write), запуск тем же абсолютным python: `<python> var/scratch/<имя>.py`; путь к проекту ставит сам скрипт — `sys.path.insert(0, str(Path(__file__).resolve().parents[2]))` до импортов `collector`.
- Временные папки (проигрывания ночей и любые черновые) не создавать в `var/scratch/` и не удалять через `find -exec` / `rm -rf`: такая команда каждый раз спрашивает разрешение. В тестах — `tmp_path` pytest, в скриптах — `tempfile.TemporaryDirectory()`: они убираются сами (решение Андрея 11.11).
- Файлы правятся только Edit/Write — не через python, heredoc, sed, awk, `echo >`. Сообщение коммита — через `-m "…"`.
- Обход песочницы (`dangerouslyDisableSandbox`) — только с вопросом Андрею в чате, не молча.
- Эти правила тимлид передаёт в промпте каждому субагенту.

## 9. Как отвечать Андрею

- Каждое сообщение начинается с метки задачи в квадратных скобках — из строки «Метка:» задания, например [ПЕРЕЕЗД].
- Простым языком, коротко, списками и таблицами. Внутренние коды и термины — с расшифровкой при первом употреблении.
- Различай факт и предположение. Утверждение о сырье без цифры от `data-checker` — предположение.
- Не пересказывай планы, промпты субагентов и промежуточные шаги: Андрею нужны вопрос остановки и сводка блока.
- Команды Андрею — по одной в сообщении; дождаться ответа, потом следующая (решение Андрея 11.11).
- Нужен ответ или действие Андрея — последняя строка сообщения: `ЖДУ АНДРЕЯ`. Ждёшь своего агента — этой строки нет.
- В конце блока — сводка 5–10 строк: ссылка на PR, что сделано одной-двумя фразами, как проверить, вопросы уровня 2 и допущения из раздела 6 описания PR. Полный отчёт — в `TEAMLEAD_REPORT.md`.

## 10. Словарь (кратко; подробно — `docs/reference/collector_architecture.md`, раздел 2)

| Термин | В коде | Что это простыми словами |
|---|---|---|
| прогон | `run` | один запуск сборщика (ночной или дневной); на диске — `night.log`, ключ `"night"` (исторические имена формата) |
| обход | `Crawl`, `CrawlState` | работа прогона по клеткам: что запросить, когда делить, когда остановиться |
| страница поиска | `search_page`, `page_url`, `classify_page` | одна страница выдачи ЦИАН по клетке (бывший жаргон SERP) |
| транспорт | `Transport`, `UrllibTransport`, `HttpxTransport`, `HttpReply` | доставить GET-запрос и принести байты ответа; выбирается флагом `--transport` |
| сайт ЦИАН | `CianSite`, `FetchedPage` | наша логика над транспортом и билетом: заголовки браузера, распаковка, длительность, сбой → код 0 |
| часы | `Clock` | «который час» и «подождать» — единственный путь времени и сна в обход |
| папка прогона | `runs/<метка>/`, `RunFolder` | всё, что прогон записал на диск; формат — `docs/CIAN_DATA_FORMAT.md` |
| клетка сбора | `tile`, `TileState` | область на карте, по которой запрашивается выдача; ключ `sector` в файлах прогона и файле клеток — историческое имя той же клетки |
| проба | `smoke` | страница 1 первой клетки очереди (обычный запрос обхода): жив ли доступ; провал — обхода нет |
| билет | `ticket`, `Ticket` | файлы `cookies.txt` и `ua.txt`, с которыми сборщик ходит на ЦИАН |
| деление | `split_into_quarters` | на первой странице клетки больше 400 объявлений — клетка режется на 4 четверти |
| дно | `floor` | уровень, глубже которого клетка не делится (3) — листается как есть |
| снимок охвата | `polygons.geojson.gz` | где сборщик искал в этот раз; НЕ путать с покрытием кода тестами |
| ступень | `ladder` | оценка прогона в `summary.json` (`ladder_result`): passed / blocked / smoke_only / invalid |
